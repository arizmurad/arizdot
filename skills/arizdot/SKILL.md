# arizdot

Control the existing Windows desktop application through `scripts/arizdot_skill.py` next to this skill. The helper locates the application from the source distribution or an installer-owned pointer and uses its local Python environment. Keep the ariztools application folder in place.

- When invoked without another action, run `python <skill-directory>/scripts/arizdot_skill.py start`. This reveals an existing indicator as well as starting a new one. The helper takes the invoking chat from `CODEX_THREAD_ID` / `CODEX_SESSION_ID` and waits for the UI to acknowledge the matching chat. If those variables are unavailable and the calling local chat UUID is known, append `--session <thread-uuid>`; do not guess an ID.
- For status, run `python <skill-directory>/scripts/arizdot_skill.py status`. To inspect a known local chat without changing navigation, append `--session <thread-uuid>`.
- Report activation success only when both `running` and `activated` are true. `already_running: true` alone is not success. If activation fails, report the helper's error and inspect the local application rather than repeatedly launching it. A stale existing instance may need one restart.
- Summarize status in the user's language: material/structure, current operation, measurements, waiting or activity reason, freshness, and next step. Explain what a returned percentage counts using `progress_scope`. A chat response finishing is not proof a scientific calculation finished; a quiet log is not proof a running process stalled.
- While arizdot monitors this task, keep the host's explicit plan current at real milestone transitions when a plan tool is available. Mark a step complete only after its outcome is verified, then set the actual next step in progress. The indicator cannot infer unreported project milestones or the next target.
- If no plan tool is available, report named milestones immediately for substantive work and at each verified transition: write a UTF-8 JSON file with `{"steps":[{"step":"Concrete milestone","status":"in_progress"},{"step":"Next milestone","status":"pending"}]}`, then run `python <skill-directory>/scripts/arizdot_skill.py report --steps-file <absolute-json-path>`. Allowed statuses are `pending`, `in_progress`, and `completed`; only one step may be in progress. Resend the full updated list at each transition and before the final answer. The helper binds it to this active conversation turn, so never reuse an earlier turn's completed plan. Percentages count completed named milestones, not tool calls or elapsed time. Do not invent a plan for a simple activation/status query. Without a plan the UI explicitly says milestone progress has not been reported.
- Send concrete commentary when actual work changes, including during long milestones. Newer commentary supersedes an older reported current-step name. Reports expire after two minutes independently of tool traffic; refresh them only from known real status, never as a blind heartbeat.
- Register EVERY actual background job started while this skill is in use, immediately after its launch is verified and before returning a reply. This includes local processes, remote notebooks, builds, exports, training and calculations. Write a JSON job file with `{"title":"Concrete work","run_id":"actual-run-identity","source":{"type":"json_file","path":"C:/absolute/status.json"}}` and run `python <skill-directory>/scripts/arizdot_skill.py job-register --job-file <absolute-json-path>`. Sources: `json_file` (path), `http_json` (HTTPS url, optional token_env name), `process` (actual local pid), `kaggle` (kernel owner/slug/version), or `reported`. Prefer an independently updating source. Never register an unstarted job, invent a PID/endpoint, treat a remote PID as local, or relaunch a job merely to monitor it. See the application's `docs/BACKGROUND-JOBS.md` for the signal schema.
- Background job IDs persist across chat turns and remain visible until dismissed. Completed replies and new prompts must not clear them. Use `job-list` to rediscover this conversation's registrations. Use `job-update --job-id <returned-id> --job-file <status-json>` only for a `reported` source, clearly distinguished from observed telemetry; it cannot supply unattended live status while the model is idle. `job-dismiss --job-id <id>` hides only the indicator entry and never stops execution. Existing jobs may be attached after verifying their launch identity; do not contact another chat or change execution as part of monitoring.
- For a NEW, already-authorized local background command, prefer `run --job-file <launch-spec>` so launch and registration happen together. The specification contains title, absolute cwd and a command argument array. The independent supervisor records real lifecycle/exit status and passes ARIZDOT_STATUS_FILE and ARIZDOT_RUN_ID to the worker for detailed progress. Use job-register for existing work; never relaunch it or start unauthorized commands.
- If the source is stale or offline, say so. Do not infer missing percentages, start or stop scientific calculations, change source bindings, modify autostart, publish the project, or contact another chat as part of simply opening the indicator or reading status.
- If a project moved to Colab/cloud, distinguish the remote observation from an old local controller. A timestamped observation is not a live cloud connection; report its age and freshness. Never test a remote PID against Windows processes.

This skill starts and queries a local desktop application. It does not add an MCP server or create a native built-in slash command; the host exposes enabled skills in its command picker.
